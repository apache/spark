How CI runs

Contributor builds

Push to a contributor branch → fork's Build workflow → tests selected from changed files → results reported on the pull request.

Upstream builds

Sampled upstream pushes → Build workflow → full test matrix. Scheduled variants provide regular coverage of extra configurations.

Branch coverage

Schedules on master → master builds or maintenance-branch dispatches → branch builds. Unchanged maintenance branches can skip a dispatch.

Recent upstream push CI

Measured usage of post-merge and other push builds on apache/spark, including master and maintenance branches.

Build-status polling

Reports contributor fork build results on pull requests.

Actual usage comes from recent Actions job timestamps, clipped to their execution hours. Running jobs count through the collection cutoff. Unavailable historical days stay blank. The Pages build starts with three measured days, expands to seven on a warm cache, and retains up to 28 days of measured history in its cache. Forecasts replay scheduled job profiles and add average upstream push usage by weekday and UTC hour. Unprofiled targets, future manual runs, skips, retries, and queue delays can change future demand. Runner-hours are unweighted execution time, without billing multipliers. Fork usage and frequent Build Status polling are outside this timeline. Normal documentation builds work offline and show configured starts.
